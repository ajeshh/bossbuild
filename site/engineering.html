B.O.S.S.

The positions it actually holds.

BOSS ships opinions about building with agents, and you should be able to interrogate them before you install anything. So: the load-bearing technical calls, stated plainly, and for every one, who it was learned from, when it was last checked, and how fast that ground moves.

None of it is welded to BOSS. Every practice below is a plain MIT-licensed Markdown file in library/practices/: readable, forkable, and arguable without installing the tool.

▸the calls

what BOSS believes

The harness is the architecture

For long-running agent work, the thing that determines whether it succeeds isn't the prompt. It's the agent-computer interface: what tools exist, what they return, how failure is surfaced, what gets verified. BOSS treats harness design as an architecture decision with an owner, not as prompt-tuning.

Verifiability decides what to automate

Work whose output can be checked automates well; work that can't be checked doesn't, no matter how good the demo looks. That line, not model capability, is how BOSS decides where an agent belongs and where a human stays in the loop.

Capability shapes, never model names

BOSS pins no model name anywhere it ships. It routes by shape (cheap and mechanical, deliberate and hard, fast and interactive) so a new model release doesn't rot anything. A new tier that changes what "cheap" means is what triggers a re-look.

Green is not the same as right

The failure mode that matters with coding agents: they rewrite assertions to match broken behaviour. So a weakened assertion is a red flag even when the suite passes, and assertion churn with no change to acceptance criteria is the loudest signal on a diff.

Most teams should not build RAG yet

The practice's whole value is telling you what not to build. Long context has eaten a lot of what retrieval used to be for; recall@k comes before anything clever; and context rot is real, so more stuffed context is not linearly better.

CLAUDE.md and AGENTS.md do different jobs

The split is not cosmetic. Host-neutral rules, how this repo is built, tested and shipped, belong in AGENTS.md, where any agent can read them. CLAUDE.md is for what's genuinely Claude-specific. Steering neutral rules into the Claude-only file is the common mistake, and it quietly locks your project to one host.

Both stay short. A context file that has grown past a screen isn't documentation; it's budget you're spending on every single turn.

A skill is a trigger before it's instructions

Most skills that don't work aren't badly written; they're never invoked. The description is the load-bearing part: it decides whether the model reaches for the skill at the right moment. Name the trigger phrases explicitly, keep one skill to one job, and put the judgment in the skill rather than expecting the caller to supply it.

Rent the runner, own the decision

Most founder "automation" is a cron job, and the categories most advice starts from are a rung too high. So it's a four-rung ladder climbed upward, and the rule at every rung is the same host-seam rule: don't author what the host already runs. Rent the execution; keep the judgment.

Three questions before anything runs unattended: what breaks if it runs wrong at 3am, who finds out, and how do you turn it off? If those don't have answers, it isn't ready to be unattended; it's ready to be a command you run.

Docs have two readers now

One is your user. The other is the model working in your repo, and it reads differently: it needs structure, canonical paths and unambiguous naming more than it needs prose. Writing for only one of them is why AI-built projects end up with docs that are simultaneously too long for a human and useless to an agent.

Agent security is its own discipline

Not web security with a chatbot on top. The lethal trifecta (private data, untrusted content, and a way to exfiltrate) is the shape to design against, and classifiers are non-deterministic, so they are mitigation and never a boundary.

▸four worth the detail

The ones that change what you'd actually do

The positions above are the shape. These four are the ones with a specific mechanism underneath, and they're the reason the rest is worth holding.

The bug that is invisible from inside your own product

The most common way an AI-built app leaks its users' data is a schema the model generated correctly and secured not at all: row-level security never configured. And the reason it survives every test you'd think to write is that the app works. Logged in as yourself, every screen is correct.

RLS-off is not a functional defect. It's a missing security property, so no happy-path test, no amount of clicking, and no screenshot will ever show it. The agent isn't confused, either: ask and it will explain RLS correctly. It simply doesn't apply it unless told. That's why BOSS treats schema as a threat topic rather than a craft one, and why the spec asks up front who must not be able to see a thing.

Sourced to the Lovable RLS class (CVE-2025-48757, rated critical, and disputed by the vendor, which the practice says out loud rather than quietly dropping).

Read the test diff harder than the code diff

When writing code was expensive, tests protected work you'd already paid for. When generating code is nearly free, verification is the only scarce thing left. The suite stops being insurance and becomes the bottleneck.

Which produces one concrete review rule: a test file that changed in the same commit as the code it tests is the highest-signal thing in the whole diff. Not automatically wrong (an intentional behaviour change should move its test) but never routine, and the one thing that must never be skimmed. The fix is ordering rather than effort: write the acceptance criteria, or the failing test, before.

And for a path a model decides: run it k times and require all k to pass. One green run against a non-deterministic system is a coin that landed your way.

Documented conventions rot. Enforced conventions compound.

An agent re-derives your codebase's conventions from scratch every session. That single fact reorganises architecture work: anything you only wrote down drifts, and anything you encoded as a check compounds. It's the difference between a convention and a gate, and with an agent in the loop the gap widens weekly rather than yearly.

So the advice is two moves, not one. Defer the architecture costs you can defer: modular monolith first, extract when a real constraint forces it, where the modular half is the load-bearing word. And spend the rigor on the one-way doors, of which the schema is the obvious one: migrations as code from day one, versioned and replayable.

And BOSS held this as a rule with no runner for about 130 releases — the exact failure it quotes. The design rung got six hooks; the code's own gate got none until smoke-guard: a dormant Stop hook that runs the smoke /smoke recorded (and the strict typecheck it folds in) when Claude finishes a turn that touched source, reports green in one line, and hands red back as a reason to keep going — once, never twice on the same failure. The Thoughtworks Radar (vol 34, April 2026) names the shape feedback sensors for coding agents and puts it at Trial: deterministic gates “wired into agentic workflows so that failures trigger timely self-correction … before a commit is made.”

A number that can only move one way

Codebases don't decay in a bad commit. They accumulate anys, TODOs, skipped tests, untyped boundaries and bundle bytes one reasonable-looking change at a time: no single diff looks bad, and the trend is the damage.

A ratchet turns the trend into a gate: pick one number, write it down, let it move only in the direction you want. And the honest limit ships with it: don't ratchet something that punishes legitimate growth, or a number that can be gamed. A metric that makes the right change look wrong gets bypassed, and a bypassed gate is worse than none.

▸when the product is the AI

“It works” is not a claim you can make about a model

If the thing you're shipping is itself AI-mediated, the usual build gates stop being enough: a smoke test proves the endpoint answered, not that it answered correctly, and nothing in your CI has an opinion about what a good answer looks like. So MVP carries a set of verbs for exactly that gap.

/spec: decide what's AI-mediated, on purpose For each feature that calls a model, write down which steps actually need it and which stay plain code, and schema the output. Cheap on day one; archaeology later.
/evals: “is it correct?” beside /smoke's “is it alive?” An eval set per AI-mediated feature, built from your own data rather than from imagined inputs. Evals-as-spec, after Hamel Husain and Shreya Shankar.
/judge-traces: error analysis on what actually happened Reads the real trace log of what the agents did and helps you sort the failures into a binary pass/fail taxonomy, not a vibes rating. The discipline is theirs too, and the binary part is the load-bearing half of it.
/ai-cost: the invoice is a product decision /ai-cost sets per-user and per-feature budgets and wires a per-call ledger; run again, it reads that ledger back and produces a dated review against the budget. An AI product whose unit cost you first meet on the bill has already made the pricing decision for you.

None of these pin a model name, same rule as everywhere else. They pin the discipline, which outlives the model.

▸how it stays true

What happens when this goes out of date

It will. The interesting question is whether anything catches it. Each practice's curve routes it to a discipline that owns re-checking it (the model curve, the protocol curve, the threat curve, the craft curve) and reviews fire on events, not just dates: a spec revision, a new frontier model, a breach, a ruling.

That matters because cadence alone provably misses. On the first freshness run everything reported fresh while the MCP practice was already wrong, seven days after it was written, because the spec had shipped in the meantime and the doc still described it as forthcoming. A calendar would not have flagged it until October.

And because boss sync pushes this guidance into live projects, a stale practice isn't inert; it actively ships bad advice. So the sweep hunts for what's wrong, not just what's missing.

make it real.
$npm install -g oyeboss
$brew install ajeshh/boss/oyeboss

Either puts boss on your PATH. Needs Node 18+ and Claude Code, in the terminal, VS Code, Cursor or JetBrains, on macOS, Linux or Windows; BOSS runs wherever Claude Code does.

The source is on GitHub and the package is on npm. MIT licensed, zero dependencies, no account.

Built by Ajesh Shah in Oakland, California; the why is here. Ajesh is on LinkedIn and GitHub.

Every byte stays on your machine. The only network call BOSS makes is when you type boss update: a GET to the public npm registry asking for a version number. Nothing is sent about you, your code, or your ideas. No analytics, no telemetry, no phone-home; the check never runs unless you ask for it. It’s ~30 lines in src/update.js and you can read them.

Where this actually is: v0.327.0, built in the open and used daily by its author. Very few other people have used it yet. BOSS is its own first project: it runs its own modes, files its own ideas, and its conscience nudges the person building it. If that sounds like a reason to wait, that’s a fair read.
